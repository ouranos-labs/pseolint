# v0.5.11 verification pass — calibration regression at HEAD

**Date:** 2026-05-06
**Triggered by:** user pushback on relying on agent-reported "zero verdict drift" claims for the v0.5.7 → v0.5.11 stack.
**Method:** ran `scripts/calibration-reputable-pseo.ts` directly against current code (ruleset v15) for the first time since 2026-05-03.

## Why this was necessary

The `tests/calibration/reputable-corpus.test.ts` test is a **soft gate** — it reads cached results from `scripts/calibration-results.json` instead of running live audits. The cached file was last refreshed 2026-05-03 at 20:22 UTC. Since then we've shipped v0.5.3 → v0.5.11 (9 releases), each touching scoring, rule logic, or new rules. Every agent that reported "reputable corpus zero new findings" was reading pre-change cached data.

**Today's run is the first calibration-against-current-code measurement since the v0.5.x stack landed.**

## Top drivers per regressed site

From `scripts/calibration-results.md`:

- **Webflow** (caution → concerning, +1): top driver `aeo/freshness-signals` (info severity, but cumulative impact pushed risk over the verdict-band threshold)
- **Jasper** (caution → concerning, +1): top driver `aeo/citable-facts`
- **Numbeo** (caution → concerning, +1): top driver `tech/canonical-consistency`

| `aeo/freshness-signals` | 6/7 | 86% | >80% — suppress for programmatic-directory |

100% / 86% fire-rates on `aeo/citable-facts` and `aeo/freshness-signals` exceed the decision-matrix threshold for site-type-specific suppression. The `programmatic-directory` profile already demotes both to `info` — but the regressed sites (Webflow, Jasper) are template-galleries that **classify as `unclear` or `small-marketing` rather than `programmatic-directory`**, so the profile demotions don't apply.

## What this means

1. **The agent-reported "zero verdict drift" claims for v0.5.7 → v0.5.11 were measured against stale data.** Real drift exists.
2. **`content/value-add` (the v0.5.8 composite) fires on 1/7 sites = 14%** — within the "<30%, keep as-is" decision band. Value-add itself is NOT the regression cause.
3. **`content/common-phrase-reuse` (v0.5.11) didn't fire on the corpus** — the ≥3-match threshold protected legit marketing copy as designed.
4. **Most likely regression source**: cumulative info-severity findings on `aeo/citable-facts` + `aeo/freshness-signals` are pushing risk score over the verdict-band boundary on sites that classify as `unclear` rather than `programmatic-directory`. The v0.5.7 sweep doc already recommended demoting `content/title-uniqueness` for `unclear` profile; that recommendation was never applied. The same pattern may apply to citable-facts/freshness on `unclear`.

## Resolution options (gates v0.6.0 cutover)

| Option | Cost | Risk |
|---|---|---|
| A) Bisect v0.5.x by reverting each release's rule additions and re-running | 5+ live audits per step × 9 releases | High accuracy; locates exact root cause |
| B) Raise `expectedVerdictCeiling` for the 3 sites from caution → concerning | trivial | Accepts regression as "real signal"; calibration corpus loses its guardrail value |
| C) Apply the v0.5.7-deferred profile demotions for `unclear` (citable-facts, freshness-signals, title-uniqueness → info or warning) and re-run | ~5 mins | Targeted fix; calibration measures impact |

**Recommendation: option C.** Apply the v0.5.7 sweep's deferred recommendations + extend to the new high-firing rules surfaced today. Re-run calibration to measure whether the 3 sites recover. If they do, ship as v0.5.12 (calibration patch). If not, fall through to option B for the remainders.

## Verification methodology going forward

The calibration test's "soft gate" design is fine for CI but not for release-readiness checks. Before each v0.5.x release going forward:

1. **Re-run `scripts/calibration-reputable-pseo.ts` directly** before claiming "no drift on reputable corpus."
2. **Compare per-rule fire-rates** against the previous run, not against the codebase intent.
3. **Inspect the per-site verdict deltas** in `calibration-results.md` for any ≥+1 ladder shifts — those are the threshold for blocking ship.

Agents working on engine changes should be told to do this re-run themselves and quote the actual numbers, not the cached file. Updated brief language: *"Re-run scripts/calibration-reputable-pseo.ts against your changes; if any site's actual verdict shifts ≥+1 ladder step compared to the latest committed scripts/calibration-results.json, document the shift before claiming the change is calibration-safe."*
