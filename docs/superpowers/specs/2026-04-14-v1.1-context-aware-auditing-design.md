# v1.1 — Context-Aware Auditing Design Spec

**Date:** 2026-04-14
**Scope:** Three features that make pseolint context-aware: page classification with per-group thresholds, auto-inferred template dimensions, and browser-rendered content analysis.

---

## 1. Page Classification

### Problem

v1.0 applies all 30 rules to all pages with identical thresholds. A 404 page, a listing page, and a pSEO template all get the same treatment. This produces noise (false positives on non-SEO pages) and misses context (pSEO pages should have stricter thresholds than marketing pages).

### Config Shape

```typescript
// pseolint.config.ts
export default {
  pageGroups: {
    pseo: {
      match: '/templates/**',
      rules: ['spam/*', 'content/*', 'links/*', 'cannibal/*', 'tech/*', 'schema/*'],
      overrides: {
        'spam/thin-content': { minWords: 500 },
        'content/unique-value': { minUniqueWords: 150 },
      }
    },
    listing: {
      match: ['/documents', '/templates', '/tools'],
      rules: ['content/*', 'tech/*', 'links/*'],
      overrides: {
        'spam/thin-content': { minWords: 50 },
        'content/unique-value': { minUniqueWords: 20 },
        'links/dead-ends': { severity: 'info' },
      }
    },
    marketing: {
      match: ['/', '/pricing', '/about', '/disclaimer', '/privacy', '/terms'],
      rules: ['tech/*', 'schema/*'],
    },
    utility: {
      match: ['**/_not-found*', '**/404*', '**/500*'],
      rules: [],
    }
  }
};
```

### Types

Add to `packages/core/src/types.ts`:

```typescript
export interface PageGroupConfig {
  match: string | string[];
  rules?: string[];
  overrides?: Record<string, Record<string, unknown>>;
}

export interface AuditOptions {
  // ... existing fields ...
  pageGroups?: Record<string, PageGroupConfig>;
}
```

### Behavior

- `pageGroups` is optional. If omitted, all pages get all rules with default thresholds. Fully backwards compatible.
- Groups are evaluated in declaration order. First match wins.
- Pages matching no group get all rules with default thresholds.
- `rules: []` skips the page entirely (excluded from scoring and pageCount).
- `rules` uses glob matching: `'spam/*'` matches all rules starting with `spam/`.
- `overrides` lets a group change rule thresholds or severity for its pages. Keys are rule IDs, values are objects merged into the rule's options.
- Glob matching against pages uses the same `matchGlob` function already in auditor.ts. Match is against URL pathname (HTTP) or relative path from source directory (filesystem).

### Scoring

- One overall score, always computed from all non-skipped pages using group-specific thresholds. A listing page with 80 words and `minWords: 50` does not generate a finding, therefore does not inflate the score.
- Output includes per-group breakdown: `groupScores: { pseo: 45, listing: 10, marketing: 5 }` alongside the existing `categoryScores`.
- `pageCount` reports total audited pages (excludes `rules: []` groups), plus `groupPageCounts: { pseo: 60, listing: 3, marketing: 6, unmatched: 18 }`.
- Cross-page rules (near-duplicate, heading-uniqueness, meta-uniqueness, keyword-collision, title-overlap) only compare pages within the same group. A marketing page is never compared against a pSEO template.

### AuditSummary Changes

```typescript
export interface AuditSummary {
  score: number;
  categoryScores: CategoryScores;
  groupScores?: Record<string, number>;
  groupPageCounts?: Record<string, number>;
  pageCount: number;
  findings: RuleResult[];
}
```

### Auditor Integration

In `auditSource`, after parsing all pages:

1. Classify each page into a group (first match wins, unmatched = default group with all rules).
2. Build a `Map<string, ParsedPage[]>` of pages per group.
3. For each group, run only the enabled rules with the group's overridden thresholds.
4. Cross-page rules receive only the pages from that group.
5. Per-page rules iterate all pages but skip pages not in a group that enables that rule.
6. Merge all findings from all groups into the final array, tagging each with `group?: string` on `RuleResult`.
7. Compute overall score from all findings (using the group-adjusted thresholds means the findings already reflect the right standards).

### RuleResult Changes

```typescript
export interface RuleResult {
  ruleId: string;
  severity: Severity;
  message: string;
  fix?: string;
  ref?: string;
  pageUrl?: string;
  relatedUrls?: string[];
  group?: string;
}
```

## 2. Fix Suggestions with Google References

### Problem

Every finding says "X is wrong" but never "here's what to do." 169 errors with no guidance is overwhelming.

### Implementation

Each rule function returns a `fix` string and a `ref` URL on its `RuleResult`. The fix text is static (template strings interpolated with page group name, thresholds, and page-specific context). No AI generation in the CLI.

Fix text is group-aware: the same rule produces different suggestions depending on the page group context. For example, `spam/thin-content` for a `pseo` group suggests adding state-specific content; for a `listing` group it suggests adding a category description.

### Formatter Changes

All four formatters render `fix` and `ref` when present:
- **Console:** fix indented under finding, ref as dim text
- **JSON:** included as fields
- **Markdown:** fix as blockquote, ref as link
- **HTML:** fix styled as a tip box, ref as hyperlink

## 3. Auto-Inferred Template Dimensions

### Problem

The tool detects that pages are similar but can't explain *why* — it doesn't understand the template matrix (profession x document x state) that generated them.

### New Rule: `spam/template-coverage`

**Category:** spam (incomplete coverage is a quality signal)
**Severity:** info
**Default config:** `templateCoverageMinPages: 5` (minimum pages in a directory before analysis runs)

### Algorithm

1. Group pages by directory (reuse `clusterKeyForUrl`).
2. For each directory with `>= templateCoverageMinPages` pages, extract the filename (last path segment, without extension).
3. Pre-mask known entities in each filename using `maskEntities` (turns `new-york` into `[STATE]` before splitting).
4. Split masked filenames by `-`. Unmasked tokens stay as-is, masked tokens become their placeholder.
5. For each token position, collect the set of unique values across all filenames in the group.
6. Token positions with 1 unique value are "constants" (template prefix). Positions with 2+ unique values are "dimensions."
7. Compute: `coverage = actual_pages / product(dimension_cardinalities)`.
8. Emit finding with dimension names, cardinalities, coverage percentage, and page count.

### Output

```
[spam/template-coverage] /templates/ has 87 pages following pattern
{profession}-{document}-{state} with dimensions:
  profession: 8 values
  document: 12 values
  state: 10 values
Coverage: 87 of 960 possible combinations (9.1%).
Fix: Low coverage may indicate missing pages or an overly broad template
matrix. Consider generating all high-demand combinations or narrowing
dimensions to what you can differentiate with unique content.
Ref: https://developers.google.com/search/docs/essentials/spam-policies#doorway-pages
```

### Edge Cases

- Multi-word entities (`new-york`) are pre-masked to `[STATE]` before tokenizing, preventing mis-splits.
- Pages with different segment counts in the same directory are grouped by segment count first, then analyzed per sub-group.
- Single-segment filenames where everything varies: 0 constant tokens = no template pattern detected, skip.
- Very high dimension counts (>20 values in a position) are likely not template dimensions but unique identifiers — flag as `info` without computing coverage.

### Config

Add to `AuditOptions.rules`:

```typescript
templateCoverageMinPages?: number;  // default: 5
```

## 4. Browser-Rendered Content (`--render`)

### Problem

Client-rendered pages (React, Next.js app router) produce HTML shells with no text content. The parser sees 0 words, triggering false thin-content findings.

### Architecture

New file: `packages/core/src/renderer.ts`

**Optional peer dependency:** `playwright-core` (4MB, no bundled browsers) in `packages/core/package.json` with `"optional": true` in `peerDependencies`.

### Connection Resolution Order

1. `--browser-ws <url>` CLI flag (highest priority)
2. `PSEOLINT_BROWSER_WS` environment variable
3. `render.browserWsEndpoint` in config file
4. Local `playwright-core` launch (requires Chromium installed separately)

Completely vendor-agnostic — works with any CDP-compatible endpoint: Browserless, raw Chromium, Puppeteer clusters, BrowserStack, etc. No vendor names in code or docs, just "CDP endpoint."

**Security:** Remote endpoints must use `wss://` (encrypted WebSocket). The renderer validates this at connection time and rejects unencrypted WebSocket URLs for non-localhost hosts. Unencrypted connections to `localhost` and `127.0.0.1` are permitted for local development only.

### Config

```typescript
export interface AuditOptions {
  // ... existing ...
  render?: {
    browserWsEndpoint?: string;
  };
}
```

CLI flag: `--render` (enables rendering) and `--browser-ws <url>` (sets endpoint).

### How It Works

**Remote URLs:** Playwright navigates to each URL, waits for `networkidle`, captures `page.content()`. This replaces the raw `fetch` response body in `LoadedPage`.

**Local directories:** Start a temporary `http.createServer` serving static files from the source directory on a random port. Navigate Playwright to `http://localhost:{port}/{relativePath}` for each HTML file. Shut down the server when done. This ensures JS execution, CSS loading, and asset resolution work correctly.

**Concurrency:** Respects the existing `concurrency` option. Opens N browser pages (tabs), processes pages through them via `runWithConcurrency`.

**Error handling:** If CDP connection fails, throw a clear error with instructions. If a single page fails to render (timeout, crash), skip it and continue (same pattern as `fetchWithRetry` returning null).

### Renderer API

```typescript
// packages/core/src/renderer.ts
export interface RenderOptions {
  browserWsEndpoint?: string;
  concurrency: number;
  timeoutMs: number;
}

export async function renderPages(
  pages: Array<{ url: string; localPath?: string }>,
  options: RenderOptions
): Promise<Array<{ url: string; html: string } | null>>;
```

### Auditor Integration

In `loadPagesFromSource`, when `options.render` is set:
- For HTTP sources: after collecting URLs from sitemap, pass them to `renderPages()` instead of `fetchWithRetry`.
- For local directories: after collecting file paths, pass them to `renderPages()` with local paths. The renderer starts a static server internally.
- The rest of the pipeline (parsing, rules, scoring) is unchanged — it receives `LoadedPage[]` either way.

### Fallback Behavior

If `--render` is passed but no CDP endpoint is configured and `playwright-core` is not installed:

```
Error: --render requires a browser connection.
  Option 1: Set PSEOLINT_BROWSER_WS=wss://your-browser:3000
  Option 2: Install playwright-core and Chromium:
    npm install playwright-core
    npx playwright install chromium
```
