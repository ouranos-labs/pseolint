# v0.6.0 cutover validation gap — must address before npm publish

**Date:** 2026-05-07
**Status:** open; gates first npm publish of v0.6.0
**Triggered by:** user directive "critique and refine before publishing"

## The finding

The v0.6.0 cutover ships `siteVerdictFromTemplates` as the default verdict source when ≥2 templates are detected (spec §15.1). The agent's calibration verification reported "zero verdict shifts" across all 9 fixture sites. **That's because the v0.6 code path was never executed**, not because it produced sensible verdicts.

All 9 fixture sites classify as `unclear` or `small-marketing`, both of which the activation gate (`canActivateV6`) blocks. The new code path runs only when classification is `programmatic-directory` / `ecommerce` / `docs` AND ≥2 templates detected.

## Root cause

The pinned/fixture-mode methodology (v0.5.12 + v0.5.15) limits each site to 25 audited URLs. The classifier in `auditor.ts:2334-2339` derives its URL set from `sitemapUrlSet` if available, else `loadedPagesRaw`. In pinned/fixture mode `sitemapUrlSet` isn't populated, so the classifier sees only the 25 pinned URLs.

```
urls.length < 50 → small-marketing (per site-classifier.ts)
```

So every fixture site gets `small-marketing` classification regardless of its true scale. v0.6 activation gate blocks → cutover code never runs.

The v0.5.15 snapshot script DOES capture `sitemap.xml` to fixture directories, but:

1. The engine doesn't currently consume it for classification (would need a small wire-through)
2. Half the captured sitemaps are HTML 404-pages, not real XML (4 of 8: ramp, wise, g2, numbeo). Only airbyte/segment/jasper/typeform have real sitemap.xml content.

## What this means for v0.6.0 release readiness

The v0.6 engine + dashboard + CLI surfaces are shipped and unit-tested. But:

- The end-to-end "real site → multi-template detection → per-template verdicts → siteVerdictFromTemplates → headline verdict" path has been validated **only with synthetic Template[] inputs in unit tests**.
- No real-world programmatic-directory site has been audited end-to-end to confirm sensible verdicts.
- Our deterministic calibration (v0.5.15's win) doesn't cover the most important code path of v0.6.0.

This is the same category of gap as the stale-cache calibration claims earlier in this session: "the test we built doesn't cover the change we made."

## Three honest paths

| Option | Cost | Risk |
|---|---|---|
| **A) Fix `discoveredUrlCount` injection** — add corpus-side override that tells the classifier "this site has N total URLs" independent of audit sample size. Engine consumes it. Re-run calibration; v0.6 path activates for sites that have ≥1000 declared URLs. | ~2 hours engine + corpus + verification | Low — clean engineering; backwards compat preserved |
| **B) Live-audit a real programmatic-directory** as a one-time smoke test (e.g., `pseolint scan https://hubspot.com/products --sample-size 100`). Confirm v0.6 fires + produces sensible output. Document. | ~15 min | Medium — single live audit, can't cover all shapes |
| **C) Publish v0.6.0 with documented gap** — ship the architectural milestone, plan v0.6.1 to address. Real customers exercise the v0.6 path on their own sites. | trivial | Medium — publishing un-validated production code, but unit tests cover the algorithmic correctness |

## Recommendation

**Option A.** It's the most rigorous and matches the user's stated preference for measurement-grounded claims. Estimated 2 hours of focused engine work:

1. Add `AuditOptions.discoveredUrlCount?: number` (or `classifierUrls?: string[]` for richer override)
2. Engine `auditor.ts:2334` uses the injected value if provided, else falls back to current behavior
3. Add `discoveredUrlCount?: number` to corpus site entries; populate based on actual sitemap size of each site
4. Re-run calibration; expect at least 2-3 sites (Wise, Segment, Jasper if their sitemaps are populated) to flip into `programmatic-directory` and exercise the v0.6 path
5. Confirm verdicts produced are sensible (don't regress past ceiling)

If the post-fix verdicts still all stay in `unclear`/`small-marketing` (because the actual sitemaps are too small or template detection doesn't find ≥2 surviving templates), that's also useful information — it tells us the v0.6 design needs real multi-template-density sites in the corpus, OR that the activation gate's threshold is too strict for the corpus shape.

## Other findings worth noting (lower priority)

- **Numbeo concerning/60 vs caution ceiling**: real calibration miss surfaced when fixtures eliminated origin errors. Pre-existing; not a v0.6 issue.
- **Segment critical/74 vs caution ceiling**: pre-existing; not a v0.6 issue.
- **Wikipedia paraphrase rule**: never tested against real-world paraphrased content. Bundled samples self-hit at 100% trivially. False-negative rate against actual paraphrasing in pSEO content is unknown.
- **value-add 7-signal boundary shift**: tests updated for the math but no broader regression. May affect borderline sites.
- **GSC dashboard LIMIT 500**: hotfix mitigation, not solved root cause. Long-term: server-side aggregation by template signature.
- **61 MB fixtures committed**: repo will balloon over quarterly refreshes. Git LFS migration candidate within next 3 months.
- **db:push/db:migrate workflow**: mutually exclusive paths conflict; production DB has been pushed but migrate journal is out of sync. Operational debt.

## Decision needed

Pick A, B, or C before first npm publish. If B or C, the calibration corpus's promise of "deterministic verdict drift detection" is degraded for the v0.6 code path indefinitely.
