# pseolint v0.6: Audit-as-Template Reframe

**Date:** 2026-05-04
**Status:** REVIEWED v1, open questions §15 resolved 2026-05-04 (see §15 footers); gating v0.6.0 implementation (task #88)
**Depends on:** v0.5.7 reputable-corpus sweep (`docs/superpowers/calibration/2026-05-04-v0.5.7-sweep.md`); bestfirenze.com self-audit signal stack (v0.5.3 → v0.5.7); change-driven monitoring design (`2026-05-01-change-driven-monitoring-design.md`); template stratification v1 (v0.5.5)

## 1. Problem statement

The audit's unit of analysis is "a URL"; every page is fetched, parsed, scored, and summarised individually. This was right for v0.4 when the canonical use-case was "audit my landing page," and survived v0.5 because monitoring just adds change-detection on top of the same per-URL pipeline. It is wrong for the use-case the brand has organised around since v0.5.3: **"audit my programmatic-SEO directory of 100k pages."**

Three concrete failures of the per-URL frame on pSEO directories:

1. **Sample dilution masks template-level issues.** A 100k-URL site sampled at 200 pages (0.2% coverage) cannot reliably detect that the `/listing/:slug` template fails `spam/thin-content` on 80k of its pages. The 200 sample slots come back with a verdict that averages across templates, drowning the signal that one template is fundamentally broken.

2. **The unit operators reason about isn't the unit we audit.** When a pSEO operator looks at their site, they see *templates* (or "page types"): the city-pair template, the integration template, the comparison template. They don't think about individual URLs. The audit currently produces 200 per-URL findings; the operator wants 5 per-template verdicts.

3. **Cross-template variance is invisible.** A site with one excellent template and one broken template averages out to "ok," but the broken template is the actual SpamBrain-trigger surface. The current findings list cannot communicate "8 of 10 sampled `/listing/*` pages fail thin-content; 0 of 10 sampled `/category/*` pages fail": that's a finding-density distribution, not a list.

v0.5.5 stratified URL sampling (commit `512bf54`) addressed (1) at the discovery layer, the budget is allocated across templates, not piled into the dominant cluster. But the engine's output stays per-URL: stratification just changes which URLs land in the per-URL findings list. The reframe is to stop flattening templates back into URLs at the output stage.

## 2. Reframe in one sentence

**v0.6 is the unit-of-analysis pivot: audit one canonical record per template plus a small variance check, instead of N URLs flattened into one findings list, one verdict per template, one site-level verdict aggregating them, and a per-template variance metric that surfaces "this template is broken on every instance" as a first-class signal.**

Two structural decisions follow:

- **Two-phase pipeline.** Phase 1 is template detection (cheap: cluster sitemap URLs, fetch a small sample for canonicality verification). Phase 2 is per-template deep audit on K samples per template (configurable; defaults: K=10 for monitoring, K=20 for re-audits). The total fetch budget = T templates × K: typically 50–100 URLs even on 100k-URL sites, vs. 200 today.
- **Per-template aggregation.** Findings carry a `template` field. Verdict is computed per-template AND at the site level. The site-level verdict aggregates per-template verdicts using a worst-template weighting (the `/listing/*` template scoring critical drags the whole site to critical, even if `/category/*` is ready).

Everything else follows from those two decisions.

## 3. Why this is the right window

v0.5.3–v0.5.7 hardened the per-URL signals (degeneration guard, blocker density floor, translation-no-op, regurgitated-content, value-add composite). The signal stack is in good shape *individually*. The remaining gap, the one bestfirenze.com surfaced and the v0.5.7 sweep confirmed, is structural: the engine still treats each URL as the analysis unit. Without v0.6, the carefully-calibrated per-URL signals keep getting averaged-out on directory-shaped sites.

Two timing constraints align here:

- **Calibration corpus is now diverse.** The v0.5.7 sweep covers SaaS catalogs (Wise, Webflow, Zapier, Typeform, Segment), AI tools (Jasper), finance (Ramp, G2), and programmatic directories (Wise currency pairs). The corpus is large enough to validate template-aware metrics and small enough to inspect individually.
- **No external lock-in on the per-URL output schema yet.** The hosted product (Pro) renders the per-URL findings list internally; we own the schema. CLI users get a JSON dump and the schema bump is a documented breaking change. Now is the cheapest moment.

## 4. New data model

### 4.1 The `Template` entity

```ts
export interface Template {
  /** Stable identifier derived from URL pattern. e.g. "/listing/:slug" */
  signature: string;
  /** Cluster size in the discovered URL set (NOT the audit sample). */
  totalUrls: number;
  /** URLs actually fetched for this template in the deep-audit phase. */
  auditedUrls: string[];
  /** Per-template grade derived from per-URL findings within this template. */
  verdict: Verdict;
  /** Per-template risk score (0-100), independent of site-level risk. */
  risk: number;
  /** Per-template category grades (integrity, discoverability, citation, data). */
  categories: CategoryGrades;
  /** Variance metric, see §5. */
  variance: TemplateVariance;
  /** Findings whose `pageUrl` is in `auditedUrls`. Reference, not duplication. */
  findingIds: string[];
}

export interface TemplateVariance {
  /** Per-rule fire-rate within the template. e.g. {"spam/thin-content": 0.8} */
  ruleFireRates: Record<string, number>;
  /** Templates with high uniformity score have consistent quality across pages.
   *  Low uniformity = some pages pass, others fail (template is incomplete or
   *  data-quality-dependent). 0 to 1, higher = more uniform. */
  uniformityScore: number;
  /** Worst-firing rule + its rate, surfaced in the template card UI. */
  topDriver: { ruleId: string; fireRate: number } | null;
}
```

### 4.2 `RuleResult` gets a `template` field

```ts
export interface RuleResult {
  ruleId: string;
  severity: Severity;
  message: string;
  pageUrl?: string;
  /** v0.6, which template the finding belongs to. Required for per-page
   *  rule firings; null/absent for site-level findings (cluster rules,
   *  cross-template rules, audit/* diagnostics). */
  template?: string;
  // ... existing fields
}
```

### 4.3 `AuditResult` shape change

```ts
export interface AuditResult {
  // ... existing site-level fields (verdict, risk, categories, headline)
  
  /** v0.6, per-template breakdown. Empty array on tiny sites where the
   *  classifier reports `unclear` or `small-marketing`; the per-URL
   *  findings list (below) carries everything. */
  templates: Template[];
  
  /** Existing per-URL findings list, preserved for backwards compat AND
   *  because per-page rules (translation-no-op, regurgitated-content,
   *  near-duplicate clusters) genuinely produce per-URL findings that don't
   *  collapse cleanly to a per-template view. */
  findings: RuleResult[];
}
```

`templates` is **additive**, old code reading `findings` still works. New code reads `templates` for the per-template view; the dashboard renders per-template cards as the primary surface, with `findings` as a drill-down detail.

## 5. Per-template variance metric

The defining v0.6 question: when 8 of 10 `/listing/*` samples fire `spam/thin-content` and 0 of 10 `/category/*` samples fire it, the engine should surface that distribution, not flatten it.

### 5.1 Per-rule fire-rate

For each (template, rule) pair: `fireRate = (samples in template where rule fired) / (samples in template fetched)`. Independent of severity, a single fire counts the same as multiple fires per page.

### 5.2 Uniformity score

A template's uniformity is **how consistent its findings are across samples**. High uniformity means "every sample has roughly the same problems" (template is broken or fine in a uniform way). Low uniformity means "some samples are clean, some are wrecked" (template depends on data quality).

```
uniformity = 1 - (mean(stdev(per-rule fire-rates across samples)))
```

Specifically: for each rule, compute the standard deviation of its per-sample fire pattern (0 or 1 per sample). Average across rules. Uniformity is `1 - avg_stdev`.

A template where every sample fires the same 5 rules → high uniformity, problem is the template itself. A template where samples fire different rules → low uniformity, problem is the data binding.

### 5.3 Top driver

The single rule that fired on the highest fraction of samples within the template. Surfaces in the template card UI as the one-line summary: "8/10 samples fail `spam/thin-content`."

### 5.4 Aggregation to site-level verdict

```ts
function siteVerdict(templates: Template[]): Verdict {
  // Worst-template weighting: if any template hits critical, site is critical.
  // If majority of templates (by URL coverage) hit concerning+, site is concerning.
  // Otherwise take the worst major template.
  const byCoverage = templates.sort((a, b) => b.totalUrls - a.totalUrls);
  const worst = templates.reduce((acc, t) => verdictRank(t.verdict) > verdictRank(acc) ? t.verdict : acc, "ready");
  // Simple v1: take the worst.
  return worst;
}
```

Calibration question (open): should one tiny template (1% of URLs) at critical drag the whole site? Probably yes for spam-trigger templates, no for cosmetic issues. Resolve in implementation phase 1 against the calibration corpus.

## 6. Engine pipeline (two-phase)

### 6.1 Phase 1: Template detection

```
Input: sitemap URLs (or filesystem path discovery)
1. Cluster URLs via `clusterUrlTemplates(urls)` (existing, from v0.5.5)
2. Filter clusters: ratio >= 0.01 (1% of total URLs) AND count >= 5
3. For each surviving cluster, sample 1 canonical URL: fetch it, run a
   minimal "is-this-actually-a-template" check (parse, verify URL structure
   matches signature, no 404)
4. Output: `Template[]` with signature, totalUrls, but no audited samples yet
```

Cost: ~T HTTP fetches where T is template count (typically 5-20). Cheap.

### 6.2 Phase 2: Per-template deep audit

```
For each template:
1. Stratified-sample K URLs from the template's cluster (K = 10 or 20)
2. Fetch + parse those K URLs (existing pipeline)
3. Run all per-page rules on those K URLs: findings carry `template: signature`
4. Compute per-template fire-rates, uniformity, top driver
5. Compute per-template verdict + risk via existing scoring with template-scoped findings
```

Cost: ~T × K fetches. For typical (T=8, K=10) on a 100k-URL site, that's 80 fetches vs 200 today, and the 80 cover all templates instead of 200 from one cluster.

### 6.3 Long-tail bucket

URLs not fitting any cluster collect into a synthetic `_longtail` template. Audited at the same K budget (or smaller, `min(K, 5)` to avoid over-investing in singletons). Verdict separately surfaced.

### 6.4 Cross-template rules

Some rules are cross-template by nature: `spam/near-duplicate` (cluster across templates), `links/orphan-pages` (graph-level), `tech/canonical-consistency` (per-page but with cross-page validation). These run once over the union of all sampled URLs, findings have `template: undefined`. They surface at the site level, not in any template card.

## 7. Schema migration

### 7.1 Engine output (`AuditResult`)

`templates` is additive. Old fields preserved:
- `verdict`, `risk`, `categories`, `headline`: site-level (now aggregated from templates)
- `findings`: per-URL list (now also tagged with `template` where applicable)
- `siteClassification`: unchanged
- `pageCount`: unchanged (total fetched)
- `diagnostics`: unchanged

New fields:
- `templates: Template[]`: empty array allowed (small sites)

JSON consumers reading the old shape continue to work. New consumers read `templates` first.

### 7.2 Hosted DB (`audits` table)

Two options:

**Option A (preferred):** `audits.scrapePlan` JSONB already carries arbitrary planning metadata. Extend with a `templates` field. No migration needed; new code reads `audits.scrapePlan.templates` and gracefully handles its absence. Old audits (before v0.6 deploy) have no `templates` and render in the legacy per-URL view.

**Option B:** New `audit_template` table joining `audit_id` → `template`. Cleaner relational model but requires migration + per-row writes.

Pick Option A for v0.6.0, defer the relational split until template-level analytics (cross-audit template trends) become a feature. The JSONB approach buys the schema-shift work for free; we can split later when we know what queries we want.

### 7.3 Findings persistence

Findings already carry a `pageUrl`. Adding `template` is a JSONB-doc shape change with no migration: new code writes the field, old data renders without it.

## 8. API changes

### 8.1 `auditSource()` return

`AuditResult.templates` added. Existing callers see no breakage. Callers that want template-aware reporting iterate `templates` and ignore the flat `findings` list (or use `findings` as a deep-link target).

### 8.2 CLI

- New `--per-template` flag on the scan command: toggles the formatter to render per-template cards (default: legacy per-URL list for now, switch default to per-template in v0.7).
- Existing `--format json` includes `templates` automatically.
- New `pseolint scan --template <signature>` flag to drill into one template's findings (handy for CI gating: fail only when `/listing/:slug` template degrades).

### 8.3 MCP

The MCP audit tool's output struct adds `templates`. AI clients (Claude Code etc.) get the per-template view automatically.

### 8.4 Web

The per-domain dashboard renders **template cards as the primary surface**:

```
/dashboard/[host]
├── site-level header (verdict + grade, unchanged)
├── template-card grid (NEW)
│   ├── /listing/:slug, D critical, 8/10 thin-content, 234 URLs covered
│   ├── /category/:slug, A ready, 0 findings, 28 URLs covered
│   └── /help/:slug, B caution, 2/10 missing-author, 12 URLs covered
└── per-URL findings list (collapsed by default, drill-down)
```

`gsc-status-strip.tsx` (v0.5.9) already renders per-template trend data, this is the v0.6 dashboard's natural pair.

## 9. Backwards compatibility

- **Engine JSON output**: additive only. Old consumers ignore `templates` and read `findings`. ✅
- **Hosted audit history**: pre-v0.6 audits have no `templates` array; the dashboard falls back to the legacy per-URL view for them. New audits render with template cards. No backfill required.
- **CLI output formatters**: `console`, `markdown`, `html` formatters get a per-template layer. Existing flat-list output preserved as a `--legacy-flat` flag.
- **Webhook payloads** (Pro alerting): the alert gate (memory: alerts_dedup table) currently fires on per-rule new findings. v0.6 adds per-template-degraded alerts ("/listing template moved from B to D") as new event types: additive.

## 10. Calibration plan

The v0.6 implementation MUST validate against the v0.5.7 calibration corpus before shipping. Expected behavior:

- **G2 (ready), Wise (caution), Webflow (caution), Jasper (caution), Ramp (ready)**: site-level verdicts must hold or improve. With template-aware aggregation, sites that have one bad template + several good ones may move *up* the ladder (the bad template no longer averages out the verdict: it's surfaced, but the site verdict respects the majority).
- **Zapier, Typeform, Segment** (currently failing past the `caution` ceiling): likely to remain critical at the SITE level because their critical findings are template-uniform (every `/integrations/:slug` page hits the same problems). But the per-template view should surface that the problem is concentrated in one template, which is the actionable signal the operator can fix.
- **Bestfirenze**: should still hit critical via the per-template path (its single template scores critical; site = critical).

False-positive risk to watch: if the variance metric is too sensitive, sites with normal data-quality variance (some pages have 6 reviews, some have 60) could flag "low uniformity → broken template" when they're just heterogeneous. Calibrate the uniformity threshold against Webflow / Wise where genuine variance exists.

## 12. Risks and unknowns

- **Variance metric sensitivity.** The `1 - mean(stdev(rule fire patterns))` formula is intuitive but untested. May produce noisy scores on small templates (K=10 samples is borderline statistical). Calibrate hard against the corpus before locking in.
- **Long-tail bucket coherence.** A "miscellaneous" `_longtail` template combining `/about`, `/contact`, `/pricing` plus genuinely-orphaned URLs may itself be too heterogeneous to score meaningfully. Possibly downgrade to "informational, not verdict-affecting."
- **Schema persistence**. Option A (JSONB extension) is fast but loses queryability. If we later want "show me all templates with `/listing/:slug` signature across all my domains' audit history," we'll need the relational split. Document the migration path.
- **CLI output size.** A site with 12 templates × per-template cards × deep findings can produce a multi-screen output. The `--per-template` view needs sensible truncation.
- **Stratification interaction.** v0.5.5 stratification samples across templates already; v0.6 leverages that. The two implementations must agree on the cluster signature (currently `clusterUrlTemplates`). If they diverge, a URL could be sampled by stratification but unattributed to any template by the v0.6 detector. Audit the integration.

- The rule set itself. No new rules, no rule logic changes.
- The verdict ladder (`ready` / `caution` / `concerning` / `critical`).
- The category model (integrity / discoverability / citation / data).
- The risk score 0-100 model.
- The site-classification system (`small-marketing`, `programmatic-directory`, etc.).
- Anything in the AEO orchestrator path.
- Pricing, billing, plan limits.

This is purely a unit-of-analysis pivot. Tiered Pro pricing (was task #80 in the original lump) is intentionally pushed past v0.6 so it can tier on the new model (per-template page caps make more sense than per-URL caps).

## 15. Resolved questions (review v1, 2026-05-04)

### 15.1 Site-level verdict aggregation rule: RESOLVED

**Decision:** site verdict = worst template's verdict, **filtered to templates with ≥5% coverage** of total discovered URLs. Templates below 5% coverage and the long-tail bucket are excluded from the verdict computation. Their findings still appear in `result.findings` and surface in the dashboard's per-URL drill-down, they just don't drive the headline verdict.

**Rationale:** straight worst-template would tank a 100k-URL site for one weird `/about` page that scored critical. Coverage-weighted average would dilute genuine SpamBrain risks (one bad template covering 30% of URLs is still a site-killer regardless of what the other 70% does). The 5% floor balances these, it's stringent enough that any *substantial* template-level failure drives the verdict, lenient enough that singleton paths can't.

**Edge case:** if NO template has ≥5% coverage (site is all long-tail / no clear template structure), fall back to the legacy single-template scoring path. The classifier already labels these `unclear` or `small-marketing`, so the v0.6 path is correctly bypassed.

**Code location:** `siteVerdict()` helper described in §5.4, implementation must apply the 5% filter.

### 15.2 K (samples per template) default: RESOLVED

**Decision:** K=10 for monitoring runs, K=20 for re-audits. Locked for v0.6.0; revisit empirically in v0.7 once we have multi-week monitoring data.

**Rationale:** at K=10 with binary fire-rates, the variance estimator's standard error is approximately ±0.15, acceptable for a "is this template uniformly broken or heterogeneous?" question. K=20 cuts to ±0.10 and is appropriate for re-audits (manual user trigger, so cost concerns are smaller). Cost: T templates × K samples, typical (T=8, K=10) = 80 fetches, vs. 200 today's flat-sample budget.

### 15.3 Template detection confidence threshold: RESOLVED

**Decision:** v0.6 detection requires **≥2 surviving templates** after the §6.1 filters (cluster ratio ≥1%, count ≥5). Sites with only one surviving template fall through to the legacy single-template path.

**Rationale:** a single template doesn't benefit from the per-template view (the template IS the site). Forcing template-card UI on single-template sites would be visual noise. The fallback gracefully handles tiny sites and homogeneous catalogs.

### 15.4 Backwards compat sunset: RESOLVED

**Decision:** `findings` flat list stays available indefinitely through v0.6.x. Sunset decision deferred to v0.7 release based on dashboard-adoption data and CLI-user feedback. NOT a blocker for v0.6.0 ship.

### 15.5 MCP shape change: RESOLVED

**Decision:** add `templates` to MCP audit-tool output as additive field. Document in v0.6.0 release notes that AI clients should iterate `templates` for the per-template view but `findings` flat list remains available. Acceptable risk given zero-MCP-adoption today.

## 16. Implementation rollout: RESOLVED (path B)

The original spec described "v0.6.0 ships in three phases as RCs." On further consideration, **path B** is cleaner: ship each phase as its own patch release with the new behaviour feature-flagged opt-in, then v0.6.0 itself is the cutover that flips the default.

| Release | Phase | Behaviour |
|---|---|---|
| **v0.5.9** (engine packages) | Engine (template detection + per-template scoring + variance metric) | `templates` field populates on `AuditResult` when ≥2 templates detected. `findings` flat list unchanged. Hosted dashboard ignores `templates` for now. Opt-in for CLI via `--per-template` flag. |
| **v0.0.10** (web only) | Dashboard | Per-domain dashboard renders template cards above the per-URL findings list when `summary.templates` is populated (rides through R2, not `audits.scrapePlan` JSONB as originally proposed in §7.2).
