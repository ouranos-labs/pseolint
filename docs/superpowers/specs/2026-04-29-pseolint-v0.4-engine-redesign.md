# pseolint v0.4 — Engine Redesign

**Date:** 2026-04-29
**Status:** GREENLIT — approved 2026-04-29 after two independent reviews
**Depends on:** dogfood self-audit run on pseolint.dev (2026-04-29 session); zero external users at time of writing

## 1. Problem statement

Three weeks of building drove the brand to "SpamBrain-proof your pSEO" + "42 rules" + a 0–100 score. A two-day dogfood run on pseolint.dev itself surfaced eight design problems that are NOT bugs in individual rules — they are shape problems with the engine and its outputs. The dogfood loop is the canonical proof point for the brand, so the same loop also reveals the engine's blind spots faster than any external user could.

This spec assumes a context that disappears the day a single external user runs `npx pseolint`: **zero install base.** No deprecation cycles, no migration guides, no semver headaches. Every breaking change in this spec is free today and prohibitively expensive in two months.

## 2. Reframe in one sentence

**pseolint v0.4 is a publish-gate that reads as confident-craft instead of accidental-iteration: one verdict, four grades, top three fixes, every finding deeplinks to a marketing page that explains it and offers the audit tool.**

Two axes lock this in:

- **Verdict, not score.** The numeric `score` field is misnamed and inverted (0=perfect, 100=worst) — even the engine's author misread it twice this session. Operators ship on verdict (`ready` vs `concerning`), not on a number that needs a translation table.
- **Four categories, not eight.** Eight is too many for any UI to render and too granular for operators to act on. Consolidate to four questions an operator actually asks: *does it deserve to rank? can it be found? will AI cite it? are inputs clean?*

Everything else in this spec follows from those two decisions.

## 3. Why this is the only window

When v0.4 ships, every choice locks in for years. This is the single window where renaming `score`, reshaping the JSON output, dropping 8 noisy rules, and consolidating 8 categories into 4 are all free moves. After the first external user, each of those choices becomes a release-cycle of migration work — usually deferred forever.

The launch story for v0.4 ("we audited our own marketing site, redesigned the engine, here's what changed") is the marketing artifact this product needs and cannot manufacture later. The dogfood work in this session is half of that artifact already.

## 4. The eight breaking changes

### 4.1 Replace `score` with verdict + grades

**Before:** `summary.score: 39` (risk score 0–100, low=good, confusing, no consistent label)
**After:**
```jsonc
{
  "verdict": "caution",     // ready | caution | concerning | critical
  "headline": "3 ship-blockers, 16 should-fix",
  "categories": {
    "quality":         { "grade": "A", "issues": 0 },
    "discoverability": { "grade": "C", "issues": 13 },
    "citation":        { "grade": "F", "issues": 17 },
    "data":            { "grade": "A", "issues": 0 }
  }
}
```

The numeric score is *gone* from the public surface. Internal `risk` value still computed for thresholding logic but not displayed. CI gates use verdict severity, not numeric thresholds: `--ci-threshold warning` is more obvious than `--threshold 40`.

### 4.2 Consolidate 8 categories to 4

| New category | Maps from | Why this name |
|---|---|---|
| **Integrity** | spam + content + cannibal | "Quality" was rejected — it implies subjective taste; the spam/* rules detect SpamBrain-classifier triggers, not low quality per se. "Integrity" covers both: are you producing original, non-deceptive, non-cannibalizing pages? |
| **Discoverability** | links + tech | Can search engines find/serve it? |
| **Citation-readiness** | aeo + schema | Will AI engines cite it? |
| **Data integrity** | data | Are inputs clean? |

Weights re-derived: Integrity 0.50, Discoverability 0.20, Citation 0.25, Data 0.05. Each category has 6–14 rules; no rule moves between categories (semantic mapping only).

### 4.3 Drop 8 noisy rules

Rules that fired more often as false-positive than as signal during the dogfood:
- `cannibal/title-overlap` (flags layout-default title inheritance as 100% match)
- `cannibal/keyword-collision` (high false-positive on /vs/ pages)
- `aeo/non-replicable-value` (doesn't recognize embedded forms reliably)
- `links/hub-pages` (misses `/rules` as hub for `/rules/[id]`)
- `tech/og-completeness` until the Next.js metadata-merge limitation is documented
- `audit/origin-readiness` (informational, has weight 0, clutters output — moved to a separate `diagnostics` field)
- `content/heading-uniqueness` (penalizes legitimately templated detail pages — needs rule rework, not just tuning)
- `content/unique-value` for hub pages (need outbound-link-density-aware threshold)

Brand becomes "**32 rules that mean something**" not "42 rules including 8 that don't". Each cut rule files an issue with the redesign criteria for re-introduction in v0.5+.

**Cannibalization use case**: cutting 2 of 3 cannibal rules effectively retires keyword-cannibalization detection in v0.4. Only `cannibal/url-pattern` (URL-shape conflicts) survives. This is intentional but consequential — the v0.4 README must explicitly state "keyword cannibalization detection is deferred to v0.5; current v0.4 detects only URL-pattern collisions" so users with that use case know to wait.

**Rule-ID stability**: ruleIds (e.g. `spam/thin-content`) are considered **stable contract from v0.4 onward**. Re-introducing a dropped rule in v0.5 must use the same ruleId if its semantics are equivalent, OR a new namespaced ID (e.g. `cannibal/title-overlap-v2`) if semantics changed. This prevents `docsUrl` rot and lets historical reports remain meaningful.

### 4.4 Reshape the JSON output schema

Top-level shape:
```jsonc
{
  "schemaVersion": "2026-04-v0.4",  // bumps on every breaking output change
  "verdict": "caution",             // verdict ladder; one of: ready | caution | concerning | critical
  "risk": 39,                       // internal risk (0–100, low=good); retained for thresholding logic, not for human display
  "summary": { "blockers": 3, "shouldFix": 16, "informational": 4 },
  "categories": { /* see 4.1 */ },
  "issues": {
    "blockers":      [{ "rule": "spam/thin-content", "url": "...", "fix": "...", "docsUrl": "https://pseolint.dev/rules/thin-content" }],
    "shouldFix":     [...],
    "informational": [...]
  },
  "diagnostics": {                  // engine-internal, weight 0, never affects verdict
    "originReadiness": { "verdict": "ready", "liveFetchCount": 28, "medianMs": 54, "p95Ms": 303, "successRatio": 0.96, "serverErrorCount": 0, "serverErrorRatio": 0, "cacheAssistRatio": 0 },
    "crawlStats":      { "discovered": 23, "fetched": 23, "skipped": 4 }
  },
  "trend": null                     // populated when --baseline provided
}
```

**Severity vocabulary is now `blockers / shouldFix / informational`** — chosen to be distinct from verdict vocabulary (`ready / caution / concerning / critical`) and category-grade vocabulary (`A–F`). The previous draft mixed `warnings` (severity) with `concerning` (verdict) in the same paragraph; this is the fix.

**`diagnostics.originReadiness` shape mirrors the existing `summary.readiness` field exactly** so the web app's `OriginReadinessCard` requires only a field-name swap, not a re-render. (The existing field is moved here, not replaced.)

**`risk` is retained at top level** as an internal numeric used for: alert-gate thresholding (see §4.9), CI exit-code thresholds with finer-grained tuning than verdict severity allows, trend deltas in `--baseline` mode. It is *never* shown in CLI/HTML/web output. Verdict + categories are the human surface.

Built for grepping, dashboarding, CI, and human reading. The current shape mixes severities in one flat array, buries verdict, and exposes implementation detail (raw weights). Flat arrays of issues per severity bucket is the shape every CI integration wants.

### 4.5 Reshape the config file

```ts
// pseolint.config.ts
export default {
  baseUrl: "https://pseolint.dev",
  detect: "nextjs",  // auto-applies framework presets

  crawl: {
    // pathname globs (NOT full-URL globs — the v0.3 footgun)
    ignore: ["dashboard/**", "api/**", "signin"],
    maxPages: 500,
    sources: ["sitemap", "internal-links"],
  },

  rules: {
    enabled: "all",
    overrides: { "spam/thin-content": { minWords: 500 } },
  },

  output: {
    format: "console",
    quiet: false,
    ciThreshold: "warning",  // verdict severity, not numeric score
  },
};
```

Key changes:
- Globs match against pathname by default (matches operator intuition; current behavior matches full URL and silently fails)
- `detect: "nextjs"` auto-applies the metadata-route ignore preset that every Next.js user currently has to discover manually
- `ciThreshold` uses verdict severity (`warning` / `concerning`) not raw score
- Warn at startup when an `ignore` pattern matches zero discovered URLs

### 4.6 First-run UX redesigned

```
$ npx pseolint http://localhost:3000
✓ Detected Next.js — auto-ignored metadata routes
✓ Discovered 23 content pages (4 utility routes skipped)
⚠ Auditing... [████████░░░░░░░] 67%

Verdict: CAUTION ⚠
Quality A · Discoverability C · Citation F · Data A

3 blockers, 16 warnings — top fixes by impact:
  1. /tools/* missing og:image (13 pages)        → add to layout.tsx
     pseolint.dev/rules/og-completeness
  2. Symptom Article schema author (5 errors)    → add author + datePublished
     pseolint.dev/rules/schema-required-fields
  3. /tools index thin unique words (1 error)    → add 36 distinctive words
     pseolint.dev/rules/unique-value

Run `pseolint --explain` for the full list.
Run `pseolint --watch` to iterate.
```

Replaces `Discovered 27 pages, fetched 26 for audit. Use --sample-size 0 for full crawl. Report written to /tmp/audit.json` with something an operator can act on in 60 seconds. Verdict + 4 grades + top 3 fixes + deeplinks to docs is the entire first-run contract.

### 4.7 Dev-server detection + grace, content-type-aware crawling

Two engine fixes that kill entire categories of false positives:

**Dev-server grace.** Detect Next/Vite/Astro/etc via response headers (`x-powered-by`, `__nextjs_*` cookies, `x-vite-*`) and apply a longer first-fetch warmup grace. The README literally says "audit your dev server" but v0.3 refuses to run on one because Turbopack hot-compile latency trips the readiness check.

**Content-type-aware crawling.** When a fetched URL returns `Content-Type: image/*` or `application/octet-stream`, skip text-based rules entirely. The dogfood found `/apple-icon` flagged as thin-content (153 words = the alt-text garbage in the binary). One-line check, kills /apple-icon, /icon, /opengraph-image, /twitter-image false positives across every Next.js user.

### 4.8 Bind the marketing site to the engine

Every rule's `docsUrl` field deeplinks to the corresponding `/rules/[id]` marketing page on pseolint.dev. The marketing pages already exist (built this session). The engine just needs to populate `docsUrl` consistently.

This makes the marketing site simultaneously the docs site simultaneously the lead-gen channel. Findings → docs → tool → audit, in one loop. Possible only with zero-user freedom because every existing `ref` URL would need a redirect contract otherwise.

### 4.9 Alert gate redesign (web app monitoring)

The web app's monitoring loop currently fires alerts on `scoreDelta >= alertDefaults.scoreDropThreshold` (a numeric drop). Removing the headline `score` would silently break this. v0.4 keeps the `risk` numeric internal field (see §4.4) and the alert gate continues to fire on `riskDelta` — direction-corrected: **alert when `risk` INCREASES by ≥ threshold** (since higher risk = worse). This is a one-line semantic flip in `monitor-domains.ts` (was: score drops by N → alert; now: risk rises by N → alert).

Schema impact: `audits.score` column is renamed to `audits.risk` (or kept as-is with a comment that "score" means risk for back-compat). `monitoredDomains.lastScore` → `lastRisk`. `monitoringAlerts.currentScore`/`previousScore` → `currentRisk`/`previousRisk`. `alertDefaults.scoreDropThreshold` → `riskRiseThreshold`. All same-shape numeric columns; rename + flip comparison direction. **Estimated effort: 1 day** (was undercounted in §6 as "~4 hours").

Implementation heads-up: `monitor-domains.ts` has TWO alert paths — `evaluateAlertGate()` (around line 181) and `maybeAlert()` (around line 238). Both read `result.score` / `d.lastScore` and both must be updated together. Missing one will cause silent alert-gate divergence.

### 4.10 Historical audit report compatibility

Existing audit JSONs in R2 storage have the v0.3 shape (`score`, 8-category `categoryScores`, flat `findings` array). New v0.4 reports have the v0.4 shape. The `/r/[slug]/page.tsx` renderer must handle both:

- Detect shape via `summary.schemaVersion` field (absent = v0.3, present = v0.4+)
- For v0.3 reports: render the legacy "Score 84/100" hero (preserved for posterity), plus a banner "This report uses the legacy v0.3 format. Re-audit for the new view."
- For v0.4 reports: render verdict + 4 grades hero
- `audits.score` (renamed `audits.risk`) DB column is retained as nullable for both eras
- The leaderboard ranks on `risk` ASC (lower risk = higher rank); existing `score` values continue to work after the rename since semantics were already "lower = better"

No backfill of historical reports — they show in their original shape forever, with a clear visual marker. **Estimated effort: ½ day** (renderer fork + banner).

## 5. What does NOT change in v0.4

- The 32 surviving rules and their detection logic (algorithm changes deferred to v0.5)
- The `@pseolint/core` package boundary (engine API for the web app stays compatible)
- AI triage (BYO key path, prompt structure, severity weights into triage)
- The OSS/Pro boundary defined in 2026-04-21 reframe
- Inngest job dispatch in the web app
- The `pseolint.config.ts` runtime (cosmiconfig stays — only the schema shape changes)
- Render mode (Playwright integration unchanged)

The v0.4 redesign is a *shape* change, not a *capability* change. Same engine, better-shaped surfaces.

## 6. Migration: zero externally, ~2 days internally

Externally: no users on v0.3, no migration cost. Internally: the web app consumes engine output through several layers (DB schema, monitoring alert gate, public report renderer, dashboard cards, leaderboard, history charts) and v0.4 requires coordinated updates. Honest estimate of internal cost:

- **DB rename + alert gate flip** (§4.9): 1 day. `score` → `risk` across `audits`, `monitoredDomains`, `monitoringAlerts`, `alertDefaults`. Drizzle migration. Update `monitor-domains.ts` comparison direction.
- **Renderer compatibility for legacy reports** (§4.10): ½ day. `/r/[slug]/page.tsx` shape-detect + dual render path + banner.
- **New shape consumers** (~4 hours): dashboard cards, leaderboard, history list, findings UI all need to read the new `verdict`/`categories`/`issues` shape. Mechanical, type-driven.

Total internal: ~2 days, fully covered in §7's Week 3 dogfood+launch slot. The day v0.4 ships:
- npm tags v0.3 as `legacy`
- v0.4 becomes `latest`
- README rewritten from scratch (not a diff)
- Schema migration runs in prod (the column rename, no data loss)
- Legacy historical reports continue to render with a "v0.3 format" banner
- No external GitHub issues to triage, no Discord support load, no user-facing migration scripts to write

If we wait another month and even five users have run `npx pseolint`, at least three of the §4 changes become a 6-week deprecation cycle each.

## 7. Implementation plan

**Week 1 — Engine surgery (5 days):**
1. Rename `score` → remove from public surface; introduce `verdict` + `grades`. Update `categoryScores` shape and rebalance weights.
2. Drop 8 rules; file follow-up issues for redesign.
3. Reshape `findings` → `issues.{blockers,warnings,informational}`. Move `audit/*` to `diagnostics`.
4. Add content-type filter to `auditor.ts` fetch path.
5. Add dev-server detection to readiness check; soften thresholds with framework signal.
6. Pathname-glob matcher for `ignore` patterns + warn-on-zero-match.

**Week 2 — Output + DX (5 days):**
7. New CLI console formatter (verdict-led output above).
8. Update HTML, markdown, JSON formatters to new schema.
9. Implement `--explain` flag (full findings list, current default behavior).
10. Implement `--watch` with cached per-page fingerprinting (delta re-audit).
11. Populate `docsUrl` on every rule pointing to pseolint.dev/rules/[id].
12. Add `pseolint diff baseline.json current.json` command.

**Week 3 — Dogfood + launch (3–5 days):**
13. Re-run pseolint against pseolint.dev under v0.4 output. Verify the new verdict + grades read as designed.
14. Update web app to consume new output schema (~4 hours: type updates + render).
15. Rewrite README from scratch.
16. Write launch post: "We audited our own marketing site. Here's what we changed in v0.4." Publish to HN, dev.to, the SEO subreddits, Twitter.

Total: ~13 working days for one engineer. Could compress to 2 weeks with parallel agents on the formatters and rule-cuts.

## 8. Risks and unknowns

**Risk: Cutting 8 rules narrows the brand from "42" to "32".** Mitigation: the dropped rules file as roadmap items with re-entry criteria; "32 rules that mean something" is a stronger story than "42 rules with known false positives".

**Risk: Verdict-led output loses CI integrators who built scripts against `score`.** Mitigation: there are no such integrators today (zero users). Past this window, this becomes prohibitive.

**Risk: Web app rebuild against new schema takes longer than 4 hours.** Mitigation: it's typed end-to-end; mechanical change. Worst case is one extra day.

**Unknown: Should we keep the "SpamBrain-proof your pSEO" tagline, or reposition for the broader rule scope?** Defer that question to a separate brand spec; v0.4 is engine-shape only.

## 9. Exit criteria

v0.4 ships when:
1. `pseolint http://pseolint.dev` returns a verdict + 4 grades + ≤3 blockers in <60s
2. The launch post is drafted
3. README rewritten end-to-end
4. The web app dashboard renders new schema without regressions
5. The 32 surviving rules each have a populated `docsUrl` pointing to a real `/rules/[id]` page
6. CI gate works on verdict severity, not numeric threshold

Verdict on the v0.4 dogfood run must be `ready` or better. If not, fix the engine OR fix the marketing site, but don't ship v0.4 until it passes its own redesigned audit. That's the dogfood contract.

- **§4.4** — Severity vocabulary changed from `blockers/warnings/informational` to `blockers/shouldFix/informational` to disambiguate from verdict ladder vocabulary (`ready/caution/concerning/critical`). Documented that `risk` (numeric) is RETAINED at top level for internal use (alert gate, CI tuning, trends) but NEVER human-displayed. `diagnostics.originReadiness` shape now mirrors the existing `summary.readiness` field exactly so the web app card needs only a field-name update, not a re-render.
- **§4.9 (new)** — Alert gate redesign: monitoring loop currently fires on `scoreDelta >= threshold`. v0.4 keeps numeric `risk` and flips comparison direction (alert when risk RISES by ≥ threshold).
